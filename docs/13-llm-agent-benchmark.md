# LLM Agent 对局测试设计（草案）

> 状态：**设计草案，未实现**。本文只定义"怎么测"，不包含任何代码。
> 文中所有"实测"数据均来自 2026-10-02 本机运行（`.poly_jump` 虚拟环境），非估算。

## 1. 目标

用 PolyJump 作为测试环境，测多个云端 LLM 的**对局能力**：

- 被测方：多个云端旗舰模型（横向对比）。
- 对手：本地最强算法（第 5 节定义怎么选）。
- 环境：A 模型 9³ 2 人局 + B 模型 R=8 2 人局。
- 产出：**完整对局记录**（含每回合 prompt / 工具调用 / 模型响应 / token / 成本），供后续离线分析。

分阶段：

- **Phase 0（原型）**：1~2 个模型、A 9³、少量局，验证接口、记录格式和流程可行性。
- **Phase 1（正式）**：多模型 × 双配置 × 多局，先后手平衡，输出可出结论的对比。

非目标（本轮不做）：

- 不做训练/微调。
- 不改游戏本体（`backend/`）规则、接口与前端。
- Phase 0 不做严格统计检验（Phase 1 再补）。

## 3. 实测约束（决定设计的关键数据）

### 3.1 动作空间与状态体积

| 配置 | 棋子数/方 | 目标格数 | 合法 action 数（开局→中局） | 全量 action JSON |
|---|---|---|---|---|
| B R=6 2P | 30 | 30 | 52 → 178（均值 135） | 8 ~ 29 KB |
| B R=8 2P | 30 | 30 | 100 → 392（均值 264） | 15 ~ 77 KB |
| A 9³ 2P | 20 | 20 | 149 → 600（均值 410） | 21 ~ 101 KB |

A 9³ 的 `state_dict()` 约 **449 KB**（729 点、7448 条边）。**原始 `state_dict` / 全量 action JSON 都不能进 prompt。**

### 3.2 紧凑文本（关键发现）

中局（60 个随机 action 后）统计：

| 配置 | 单棋子落点数（中位/最大） | 单棋子落点文本 | 全部棋子落点文本 | 全部棋子含路径文本 |
|---|---|---|---|---|
| B R=8 | 8 / 18 | 97 字符（max 174） | **2.9 KB 字符** | 6.5 KB |
| A 9³ | 18 / 28 | 205 字符（max 349） | **4.1 KB 字符** | 11.6 KB |

紧凑格式示例：`(6,0,0): (5,1,0) (4,2,0) (4,0,-2)`

结论：**全量信息用紧凑文本是可行的**（A 全量约 1k token/回合），瓶颈在 JSON 序列化而非信息本身。

### 3.3 路径唯一性

实测（B R=8 / A 9³ 中局）：**同一落点只对应唯一路径**（重复落点数 0/30、0/20）。
因此"棋子 + 落点"足以唯一定位一个 action，接口可以只传落点，由环境解析路径。

### 3.4 对局长度

`graph_bfs` 自对弈、跑到终局：

| 配置 | 对局 action 数 | 本地耗时 |
|---|---|---|
| B R=8 | 323（P1 胜） | 3.5 s |
| A 9³ | 136（P2 胜） | 4.9 s |

一局 100~400 个 action ⇒ **上下文不能跨回合累积**（第 9 节）。

### 3.5 本地算法耗时

| 算法 | B R=8 单步 | A 9³ 单步 |
|---|---|---|
| `graph_bfs` | < 0.01 s | < 0.01 s |
| `mcts`（20 模拟） | 7.2 s | 12.2 s |
| `mcts`（100 模拟） | 35.4 s | 62.5 s |

MCTS 当对手时（仅对手思考时间）：

| | 20 模拟 | 100 模拟 |
|---|---|---|
| B R=8（323 步） | ≈ 39 分钟 | ≈ 3.2 小时 |
| A 9³（136 步） | ≈ 28 分钟 | ≈ 2.4 小时 |

结论：MCTS 做正式对手必须限定模拟次数；Phase 0 用 `graph_bfs`。

## 4. 对局配置

与现有基准（`ai_research/runner.py` 的 `make_a_config` / `make_b_config`）保持一致：

| 项 | A 主配置 | B 次配置 |
|---|---|---|
| 几何 | A，9×9×9，方向集 `[6,12,8]`，layers=4 | B，R=8 |
| 玩家 | 2 | 2 |
| 移动 | 单步 + 跳 + 连跳，`FREE_STOP`，`two_hop=False` | 同左 |
| 吃子 | 无 | 无 |
| 计分 | 关闭 | 关闭 |
| 胜利 | 填满对方目标区（`must_fill_all_cells=True`） | 同左 |
| 单局上限 | 建议 400 action（实测 136 完成） | 建议 800 action（实测 323 完成） |
| 先后手 | 轮流（同一对局组合跑偶数局） | 同左 |

## 5. 对手：本地最强算法

"本地最强"目前**没有定论**：`docs/12` 记录 MCTS 与三种启发式在 R=4 的 80 action 内均未分胜负。需要先定：

**Phase 0 资格赛**（纯本地，无 API 成本）：

- 参赛：`graph_bfs`、`mcts@20`、`mcts@100`（可选加 `euclidean`、`chebyshev`）。
- 场地：B R=6 2P（快），round-robin，每对 N 局（建议 ≥ 10），跑满到终局。
- 判据：胜率 > 对局时长（MCTS 很慢，见 3.5）。
- 产出：胜者写入 `experiment.json` 的 `opponent` 字段，成为后续所有 LLM 对局的固定对手。

**倾向**：Phase 0 用 `graph_bfs`（快、确定性强、无随机性）；若资格赛证明 MCTS 明显更强，Phase 1 换 MCTS 并把模拟次数固定。

## 6. 交互接口（核心选型）

### 方案 A：工具查询式（你描述的形态）

每回合：给状态 → 模型调用 `get_moves(piece)` 若干次 → 调用 `move(piece, dest)`。

工具集（草案）：

| 工具 | 参数 | 返回 |
|---|---|---|
| `get_state` | — | 紧凑棋盘（见第 7 节） |
| `get_moves` | `piece: [x,y,z]` | 该棋子全部合法落点（紧凑文本） |
| `move` | `piece: [x,y,z]`, `to: [x,y,z]` | 执行结果（是否合法、是否终局） |

- 优点：信息量可控（单次查询 97~349 字符）；几何/规则合法性外包给环境；测"检索 + 决策"。
- 缺点：每回合 1+k 次 API round-trip（成本与延迟 ×k）；测的是 **agent 能力**，不是裸模型能力。
- 风险：模型可能"乱查"（查完不用）或"不查就猜"，需要单独统计。

### 方案 B：全量紧凑候选（对照臂）

一次调用给**全部棋子**的落点（实测 A 仅 4.1 KB 字符），模型输出 `piece + dest`。

- 优点：1 call/回合，最便宜、最确定、实现最简单；无 round-trip 放大。
- 缺点：不测查询策略；长列表可能有位置偏差。
- 定位：与方案 A 同模型对照，可**分离"会不会找信息"与"决策质量"**。

### 方案 C：自由输出路径（后续可选）

只给规则 + 棋盘，模型自己写路径（如 `[[0,0,0],[1,1,0],[2,2,0]]`），环境校验，非法重试。

- 优点：最接近"裸模型能力"，测空间推理。
- 缺点：非法率高；A 模型几何（三套方向）难解释；容易把"格式失败"混进"能力失败"。

### 方案 D：写策略代码（另一类测试）

模型离线写策略函数，由 runner 执行。成本最低、可复现，但测的是编码 + 算法设计，不是实时决策。本轮不采用。

### 推荐

- **Phase 0：方案 A**（按你的描述），只跑通 1 个模型。
- **Phase 1：A 为主臂 + B 为对照臂**（同一模型两种接口），C 视需要再加。

## 7. 观测与提示词

状态块（草案，紧凑文本）：

```text
You are P1. Goal: fill ALL 20 cells of your target region with your pieces.
Your pieces (20): (0,1,0) (2,1,0) (0,3,0) ...
Opponent pieces (20): (8,6,8) (7,8,5) ...
Your target region (20 cells): (8,7,8) (8,8,6) (6,8,7) ...
Progress: you 3/20, opponent 5/20. Round 41. Last action: P2 (7,6,8)->(7,5,7).
```

- 状态块约 800~900 字符（≈ 250 token）。
- 规则摘要：从 `docs/03-game-rules.md` 压缩为固定文本（跳、连跳、目标区、胜负），**版本化**。
- 提示词模板放 `prompts/v1.md`，运行时记录内容 hash，保证不同模型、不同批次用的是同一份提示词。

## 8. 回合协议与失败处理

| 场景 | 处理 |
|---|---|
| 每回合工具调用上限 | 默认 8 次（`get_moves`），超限强制要求 `move` |
| 非法 `move` | 重试 ≤ 2 次；仍失败 → 回退 `graph_bfs` 动作并标记 `fallback=true` |
| 单次 API 超时 | 默认 60 s；超时按失败计 |
| 输出格式错误 | 计入失败率，不静默修正（除非只是 JSON 包裹问题） |
| 到达单局上限 | 按"目标区棋子数 → path 更短"判优（口径需与 `metrics.py` 对齐后固定） |

所有失败都要写进记录，**不允许静默兜底**，否则指标失真。

## 9. 会话与上下文策略

**每回合独立上下文（推荐）**：每次 `choose()` 只发"系统提示 + 当前状态 + 最近 K 步（K=6）+ 本回合工具往返"，回合结束丢弃。

理由：

- 一局 136~323 个 action，整局累积对话必然爆上下文。
- 独立上下文使每回合 token 可预测、成本可估算、对局可复现。

代价：模型没有跨回合的"长期记忆"（例如自己制定过的计划）。这本身就是一个可记录的现象（Phase 1 可加"连续对话"对照臂，但需处理截断策略）。

## 10. 记录与归档

沿用 `ai_research/runs/<时间戳>/`，扩展：

```text
runs/<时间戳>/
├── experiment.json        # 增加 models[]、prompt_hash、opponent、温度、种子
├── matches/<game_id>.json # 完整对局（action 序列 + 结果 + 指标）
├── llm/<game_id>.jsonl    # 每回合一条：prompt、工具调用、响应、token、延迟、成本
├── metrics.json
└── summary.md
```

每回合记录字段：

```text
turn, player, model, state_hash, messages[], tool_calls[],
chosen_action, legal, retries, fallback, latency_ms,
tokens_in, tokens_out, cached_tokens, cost_usd, cumulative_cost
```

## 11. 指标

**对局层**（复用 `metrics.py` 口径）：

- 胜负、action 数、终局目标区棋子数。
- path / detour（与同局 `graph_bfs` 对手对比）。

**Agent 层**（新增）：

- 平均每回合工具调用数、无效查询率（查了不用的比例）。
- 非法输出率、回退率、超时率、格式错误率。
- 每回合 token / 成本 / 延迟（P50 / P95）。

**失败模式分类**（离线分析用）：

- 方向性错误（朝远离目标区走）、往返重复（进目标区又出来）、乱查（查询分布与决策无关）、格式失败、上下文/超时失败。

## 12. 成本与时间预算（粗估）

单回合输入 ≈ 系统提示 800 + 状态 250 + 工具往返 100~300 ≈ **1.2~1.4k token**；
方案 A 每回合 2~4 次调用 ⇒ **3~6k token/回合**；方案 B 每回合 1 次调用 ⇒ **~1.5k token/回合**。

| 配置 | LLM 回合数 | 方案 A 输入 token | 方案 B 输入 token |
|---|---|---|---|
| A 9³ | ~68 | ~0.3 M | ~0.1 M |
| B R=8 | ~161 | ~0.7 M | ~0.25 M |

（按 $1/M 输入计：A 方案 ≈ $0.3~0.7/局/模型，B 方案 ≈ $0.1~0.25/局/模型；具体价格按各 provider 实际计算。）

时间：单局 = LLM 回合数 × 每回合延迟（2~4 次调用 × 3~10 s）≈ **20~90 分钟/局**；对手若用 MCTS 再加 39 分钟（B R=8）。**Phase 0 必须用 `graph_bfs` 对手。**

## 13. 公平性与可复现性

- 同一提示词版本、同一工具 schema、同一对手、同一配置。
- 温度固定（建议 0 或最低档），记录 provider 侧的模型版本号（不接受浮动 alias，如 `latest`）。
- 每个"模型 × 配置"跑偶数局，先后手各半。
- 记录失败与重试，回退动作不能算作模型决策。
- 数据污染备注：PolyJump 是自研 3D 变体，不在公开棋谱里；但"中国跳棋"先验可能被模型带进来，需在分析时注明。

## 14. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 上下文爆炸 | 对局中断 | 每回合独立上下文（第 9 节） |
| API 限流 / 超时 | 对局不完整 | 重试 + 标记；记录原始错误 |
| 非确定性 | 结果不可复现 | 固定温度/种子；多局取分布 |
| 成本失控 | 预算超支 | Phase 0 先小样本；跑前估算 + 上限 |
| 回退动作污染指标 | 指标失真 | 单独标记并单独统计 |
| 模型"知道答案"（跳棋先验） | 结论偏差 | 分析时注明；不据此下强结论 |

## 15. 分阶段计划

**Phase 0（原型）**

1. 本地资格赛：确定"本地最强算法"（第 5 节）。
2. 实现 `ai_research/llm/` 最小模块（第 16 节）+ 1 个 provider。
3. 1~2 个模型 × A 9³ × 3 局（对手 `graph_bfs`）。
4. 产出：跑通结论 + 完整记录样例 + 单局成本实测（用于校准第 12 节估算）。

**Phase 1（正式）**

1. 扩到多 provider、多模型。
2. 每个模型 × A/B 双配置 × N 局（先后手平衡）。
3. 方案 A + 方案 B 双接口对照。
4. 产出：`summary.md` + 失败模式分析 + 成本报告。

## 16. 代码结构建议（不改游戏本体）

```text
ai_research/llm/
├── agent.py        # LLMAgent(Agent)：choose(env) -> action，内部处理工具往返
├── provider.py     # 各 provider 的 chat/tool-call 适配（OpenAI 兼容优先）
├── tools.py        # get_state / get_moves / move 的定义与调度
├── prompts/v1.md   # 版本化提示词

```

runner 侧：`--agents` 支持 `llm:<model>` 语法（现有 registry 是类名映射，需要一个轻量工厂）。
